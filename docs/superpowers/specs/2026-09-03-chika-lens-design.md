# Chika Lens — 도쿄 생활 입지 분석 & 대화형 추천 에이전트

- 작성일: 2026-09-03
- 개정: 2026-09-04 — Places Insights(BigQuery)가 **개인에게 제공 불가**로 거절되어
  **Places Aggregate API**로 전환. §3, §6.2(지표 12), §8, §9, §10, §11 갱신.
- 상태: Phase 0 완료, Phase 1 진행 중

## 1. 배경과 목적

도쿄에 거주하는 한국인이 "어디에 살까"를 결정할 때, 일본어 부동산 사이트는
일본인 기준의 정보만 준다. 한국인에게 실제로 중요한 축(한국 식자재 접근성,
외국인 임대 난이도, 서울 어느 동네와 비슷한가)은 어디에도 정리되어 있지 않다.

본 프로젝트는 Google Places Aggregate API와 일본 공공데이터를 결합해
도쿄 역세권을 정량 평가하고, OpenAI Agents SDK 기반 대화형 에이전트로
한국인 관점의 지역 추천을 제공한다.

- 성격: 학습·포트폴리오 프로토타입
- 범위: 도쿄 23구
- 언어/스택: Python(에이전트·분석) + Next.js(채팅·지도)

## 2. 유스케이스

### 2.1 메인: 조건 대화 → 역세권 랭킹

사용자가 자연어로 조건을 말하면 에이전트가 가중치로 변환하고, 역세권 약 250개를
점수화해 상위 5곳을 지도와 함께 제시한다. 조건이 모호하면 **되묻고 확정한 뒤에만**
랭킹을 실행한다.

결과 화면이 답하는 것:

| 질문 | 근거 |
|---|---|
| 왜 여기가 1위인가 | 지표별 기여도 분해 |
| 실제 시세는 얼마인가 | MLIT 거래가격·지가공시 |
| 한국인이 많은가 | 구별 한국 국적 비율 (구 단위임을 명시) |
| 서울로 치면 어디인가 | LLM 서술 (데이터 아님, 감각 번역) |
| 단점은 무엇인가 | 감점 지표를 숨기지 않고 명시 |

### 2.2 파생

1. **후보지 비교** — 2~3곳을 나란히 놓고 차이 나는 축만 강조
2. **조건 되돌리기** — 예산·통근 조건만 바꿔 재랭킹 (대화 상태 유지)
3. **가치 갭 탐지** — 시세를 지표로 회귀시켜 저평가 역세권 발견

### 2.3 v1에서 하지 않는 것

- 매물 검색 (SUUMO 등 스크래핑은 ToS 위반 소지) — 시세 통계까지만
- 통근 시간 실측 (Routes API 비용) — 역 간 소요시간 테이블로 근사
- 도쿄 외 지역 (샘플 데이터셋이 도쿄만 커버)
- **치안 지표** — 警視庁이 町丁目 단위 범죄 데이터를 공개하지만, 역세권 단위로
  재집계하는 별도 파이프라인이 필요해 v1 범위를 넘는다. v2 후보

### 3.1 Places Aggregate API — 능력과 제약

Places Insights(BigQuery)를 쓰려 했으나 **개인 신청은 제공 불가**로 거절됐다(2026-09-04).
Google이 대안으로 제시한 Places Aggregate API로 전환한다.

`computeInsights` 한 번이 "이 영역 안에, 이 타입이고, 이 조건에 맞는 장소가 몇 개인가"에
답한다.

| 필터 | 값 |
|---|---|
| 영역 | 원(중심+반경) / 행정구역(place ID) / 임의 폴리곤 |
| 타입 | `includedTypes` / `excludedTypes` / `includedPrimaryTypes` (배열) |
| 영업상태 | `OPERATIONAL` / `PERMANENTLY_CLOSED` / `TEMPORARILY_CLOSED` |
| 가격대 | `FREE` ~ `VERY_EXPENSIVE` |
| 평점 | `minRating` / `maxRating` (1.0~5.0) |

응답은 `count`, 그리고 **count가 100 이하이면 `place ID` 목록**까지 준다.

**Insights 대비 잃는 것**

- **속성 필터가 없다.** `good_for_children` 같은 약 70개 속성을 쓸 수 없다.
  지표 12를 타입 기반으로 교체했다 (§6.2)
- **자유 SQL이 없다.** H3 그리드 집계, 타입별 일괄 집계 같은 것을 못 한다.
  필요한 조합마다 콜을 한 번씩 써야 한다

**Insights 대비 얻는 것**

- **4주 평가 기간이 없다.** 이전 설계의 최대 시한 리스크가 사라졌다
- **BigQuery 의존이 사라진다.** Analytics Hub 구독도, 데이터셋 권한도 불필요
- **place ID를 영구 보관할 수 있다** (캐싱 제한에서 명시적 면제). 한식당처럼
  희소한 카테고리는 count ≤ 100이라 실제 place ID가 오므로, "Insights에 이름이
  없다"는 문제가 구조적으로 해소된다
- **임의 폴리곤**을 쓸 수 있어, 나중에 원형 800m를 실제 도보권 폴리곤으로
  바꿀 여지가 생긴다

**남는 제약**

- **한국 식자재점 전용 타입은 여전히 없다** (`grocery_store`에 섞임).
  Places API Text Search로 1회성 배치 보완 — 이전 설계와 동일

### 3.1.1 비용과 갱신 주기

무료 5,000콜/월(Pro SKU), 분당 1,200콜.

**역이 489개다.** 초기 설계는 250개로 잡았으나 국토수치정보 실데이터로 역 마스터를
만들어 보니 도쿄 23구의 고유 역명은 489개였다(§6.1.1). 전부 매달 갱신하면
489 × 17 = **8,313콜**로 무료 한도를 66% 초과한다.

**해결: 갱신 주기를 지표별로 나눈다.**

| 배치 | 지표 | 콜 | 주기 |
|---|---|---|---|
| 코어 | 1, 4, 5, 6, 7, 8, 9, 12, 15 (9개) | **4,401** | 월 1회 |
| 다양성 | 10 (요리 8종) | 3,912 | 6개월 1회 |

근거는 데이터의 성질이다. 편의점·병원 개수는 달마다 움직이지만 **한 동네의 요리
구성비는 그렇지 않다.** 나카노가 일식 70%인 것은 반년 뒤에도 그렇다. 매달 다시
셀 이유가 없다.

부트스트랩 달에만 8,313콜로 한 번 초과하고(신규 계정 $300 크레딧으로 흡수),
그 뒤로는 코어 배치가 계속 무료 한도 안에 들어간다.

역 근접 통합으로는 해결되지 않는다 — 500m 이내를 전부 합쳐도 390역 × 17 =
6,630콜이고, 그러면 "신주쿠역"이 사라져 사용자가 말하는 단위와 어긋난다.

QPM 1,200 제한상 코어 배치는 최소 4분 소요.

집계 수치의 보관 기한은 Aggregate API 정책 문서가 명시하지 않는다. Maps Platform
일반 약관의 **30일 캐시 제한**이 적용될 가능성이 높으므로, 인덱스를 **최소 30일마다
갱신**한다. 월 1회 배치이므로 실무상 제약이 아니다. place ID는 영구 보관 가능하다.

**귀속 표기 의무:** 원시 카운트를 화면에 그대로 노출하면 "Google Maps" 표기가
필요하다. 다만 우리가 가공한 점수·퍼센타일에는 귀속이 불필요하다 —
정책상 "Google은 Google Maps 콘텐츠에만 귀속되며 당신의 값에는 아니다".

### 3.2 해상도 불일치 처리

랭킹 단위는 역세권이지만 국적별 인구 데이터는 구 단위까지만 존재한다.
같은 구 내 모든 역이 동일 값을 갖게 되므로:

- **주력 신호**: 한국 인프라 밀도 (역세권 해상도, Places Aggregate API)
- **배경 보정**: 구별 한국인 거주 밀도, 구별 외국인 비율 (낮은 가중치)
- 결과 화면에 "이 지표는 구 단위입니다"를 **명시 표기**한다

## 4. 아키텍처

의존 방향은 항상 안쪽을 향한다. `domain`은 외부를 import하지 않는다.
OpenAI SDK가 `domain`에 등장하면 설계 위반이다.

```
interface/     FastAPI 엔드포인트 + Agents SDK 툴 정의 (얇은 어댑터)
   ↓
application/   유스케이스: RankAreas / ExplainArea / CompareAreas /
               DetectValueGap / LookupPlaces
   ↓  (포트 인터페이스에만 의존)
domain/        Station, AreaMetrics, Weights, AreaScore, SearchCriteria
               ScoringService, ValueGapAnalyzer   ← 순수 파이썬, 외부 의존 0
   ↑  (구현)
infrastructure/ AggregateAreaRepository, MlitPriceRepository,
                PlacesApiClient, TokyoStatsLoader
```

## 5. 에이전트 계층

### 5.1 핵심 원칙

**점수 계산은 도메인이 하고, LLM은 절대 계산하지 않는다.** LLM의 역할은
두 가지뿐이다 — (1) 조건을 `Weights`로 번역, (2) 결과를 한국어로 서술.
그래야 같은 조건에 같은 답이 나오고, 랭킹 로직을 LLM 없이 테스트할 수 있다.

### 5.2 구성: 2 에이전트 + in-process 핸드오프

A2A 프로토콜이 아니다. 같은 프로세스·같은 대화 이력 안에서 제어권만 넘긴다.

**`IntakeAgent`** — 조건 수집. 출력은 자연어가 아니라 구조화 타입.

```python
class SearchCriteria(BaseModel):
    commute_to: str | None
    commute_max_minutes: int | None
    budget_yen: tuple[int, int] | None
    household: Literal["single", "couple", "family"]
    weights: Weights
    hard_filters: list[str]
```

**`AnalysisAgent`** — 툴 호출과 결과 해석.

| 툴 | 유스케이스 | 데이터 |
|---|---|---|
| `rank_areas(criteria)` | RankAreas | BigQuery 사전 인덱스 |
| `explain_area(station_id)` | ExplainArea | 지표별 기여도 분해 |
| `compare_areas(ids[])` | CompareAreas | 차이 나는 축만 추출 |
| `detect_value_gap(filters)` | DetectValueGap | 회귀 예측가 vs 실거래가 |
| `lookup_places(station_id, category)` | LookupPlaces | Places API 실시간 |

### 5.3 가드레일

1. **범위 이탈** — 도쿄 23구 밖 질문 거절 (데이터 없음 → 환각 위험)
2. **투자 조언 금지** — 데이터만 제시하고 판단은 사용자에게 반환.
   특히 가치 갭 출력에는 면책 문구를 강제 삽입
3. **수치 환각 차단** — 툴 결과에 없는 숫자가 서술에 등장하면 출력 검증에서 차단

### 5.4 프론트 연동

Agents SDK 스트리밍을 SSE로 전달하되 **텍스트와 툴 결과를 분리**한다.
`rank_areas` 반환 즉시 프론트가 지도에 핀을 찍고, 그 뒤에 서술이 타이핑된다.
지도가 설명보다 먼저 뜨는 편이 체감이 낫다.

### 5.5 대화 상태

Agents SDK 세션 메모리로 `SearchCriteria`를 유지한다. "예산 12만엔으로 낮추면?"이
오면 해당 필드만 교체해 재랭킹한다 (유스케이스 2.2-2의 구현).

## 6. 스코어링

### 6.1 분석 단위

도쿄 23구 내 철도역 **489개**, 각 역 반경 800m(도보 10분). 역 기준을 택한 이유:
일본 부동산 검색이 역 기준이고, Aggregate API의 `circle` 필터(중심 좌표 + 반경)와
직접 맞물리며, 사용자가 "나카노역 근처"라고 말한다. 인접 역의 반경이 겹치는 것은
그대로 둔다 — 실제로 비슷하기 때문이다.

### 6.1.1 역 마스터 실측 (2026-09-04)

국토수치정보 N02(철도, 令和4년판) + N03(행정구역, 東京都)로 역 마스터를 만든 결과
**489개**가 나왔다. 초기 추정 250개는 과소평가였다 — 도쿄 23구에는 JR·지하철·사철이
촘촘히 깔려 있다.

검증 결과:

- 구별 분포가 실제 면적과 일치 (大田区 39 ~ 目黒区 10)
- 주요 역 좌표·구·노선 수 정확 (나카노 `35.7057,139.6656`, 신주쿠 7개 노선)
- **같은 이름의 다른 역으로 인한 오병합 0건.** 23구 안에서 역명은 고유했다.
  N02에 `N02_005g`(역 그룹 코드)가 있어 향후 더 엄밀한 병합도 가능하다

이 489라는 수가 콜 예산 전제를 깨뜨렸다 (§3.1.1).

**역명은 일본어 표기만 쓴다** (2026-09-04 결정). `Station`에서 `name_ko`를 제거했다.

한국인 대상 서비스지만 역명을 한글로 음차하지 않는다 — 도쿄에 사는 사람은
그 이름으로 부동산 사이트를 검색하고 표를 산다. `北千住`를 "기타센주"로 바꾸면
읽기는 쉬워져도 실제로 쓸 수 없는 문자열이 된다. 서술은 한국어, 고유명사는
일본어라는 분리다.

`AnalysisAgent` 지침에 "역명을 한글로 음차하지 말 것"을 명시했다. 명시하지 않으면
LLM이 친절하게 변환해 이 결정을 무효화한다.

| 10 | `restaurant_variety` | 음식점 다양성 | Aggregate | 요리 타입 8개 각각 1콜, **유효 종 수** exp(H) | + |
| 11 | `childcare_education` | 보육·교육시설 접근성 | MLIT | — | + |
| 12 | `child_friendly_venue` | **아이 동반 시설 밀도** | Aggregate | `playground`+`amusement_park`+`zoo`+`aquarium` 한 콜 | + |
| 13 | `price_level` | 시세 수준 (역세권 중앙값) | MLIT 거래가격 | — | − |
| 14 | `disaster_risk` | 재해위험 (침수·지반) | MLIT | — | − |
| 15 | `nuisance_venue` | 감점 상권 | Aggregate | `storage`+`car_repair`+`car_wash`+`truck_stop` 한 콜 | − |

**지표 12가 바뀐 이유:** 원래는 `good_for_children` 속성이 붙은 시설의 비율이었으나
Aggregate API에 속성 필터가 없다. 타입 기반의 "아이 데려갈 곳 밀도"로 대체했고,
이쪽이 사용자에게 더 직관적이기도 하다 — "아이 동반 가능 표시된 가게 비율"보다
"놀이터·수족관이 몇 개 있나"가 읽기 쉽다.

**지표 10의 비용 주의:** `includedTypes` 배열은 합계 하나만 돌려주므로 타입별
분해가 안 된다. 다양성을 세려면 요리 타입마다 콜을 써야 한다. 무료 한도에 맞춰
대표 8개 타입으로 제한한다.

### 6.2.1 실측이 바꾼 두 지표 (2026-09-04, 나카노역 800m)

`scripts/probe_aggregate.py`로 실제 API를 때려 본 결과 지표 두 개가 설계대로는
쓸 수 없다는 것이 드러났다.

**지표 15 — `bar`·`night_club`을 뺐다.** 원래 구성(`storage`+`car_repair`+`bar`+
`night_club`)의 나카노 실측은 382였고, 분해해 보니 `bar` 310(65%) + `night_club`
105(22%)로 88%가 유흥이었다. 원래 의도한 창고·정비소는 39개(8%)뿐이다.

문제는 크기가 아니라 **신호의 방향**이다. `bar` 310은 "유흥가"가 아니라 "먹고 마실
데가 많은 동네"를 뜻하고, 도쿄 역세권에서 그건 대체로 장점이다. 감점으로 뒤집으면
활기찬 역일수록 벌점을 받는다. 게다가 `bar` 310은 `japanese_restaurant` 455와 같은
스케일이라, 요식업 밀도를 한 번은 플러스로 한 번은 마이너스로 이중 계상하게 된다.

→ `storage`+`car_repair`+`car_wash`+`truck_stop`으로 좁혔다(실측 39). 소음·대형차
통행·경관 측면에서 주거 쾌적성을 실제로 떨어뜨리는 것만 남겼다. 유흥의 소음은
가치판단이 갈리고 영업시간 데이터가 필요하므로 v2 과제로 미룬다.

**지표 10 — 종 수에서 유효 종 수로 바꿨다.** 원래는 count > 0인 타입 수였는데
나카노가 **8/8**이었다. 도쿄 23구에서 이 8개 타입이 하나라도 없는 역은 거의 없으므로
250개 역이 전부 만점이 되어 아무것도 구분하지 못한다.

→ 섀넌 엔트로피의 유효 종 수 `exp(-Σ p·ln p)`로 바꿨다. 한 타입이 압도하면 1에,
고르게 분포하면 타입 수에 가까워진다. **콜 수는 그대로**이고 계산만 다르다.
나카노는 일식이 70%(455/653)라 **3.13 / 8**이 나온다.

**응답 파싱 주의:** `count`는 정수가 아니라 **문자열**로 온다(`"42"`). protobuf의
int64가 JSON에서 문자열로 직렬화되기 때문이다. 어댑터에서 `int()` 변환을 빠뜨리면
퍼센타일 정규화가 문자열 비교로 조용히 망가진다 — `"9" > "42"`가 참이 된다.

통근 시간은 지표가 아니라 **하드 필터**다. 상한을 넘는 역은 점수와 무관하게 제외된다.

### 6.3 정규화: 퍼센타일 랭크

원시값을 그대로 쓰면 편의점 개수(0~80)가 재해위험(0~1)을 압도한다.
250개 역 안에서 퍼센타일(0~100)로 변환한다.

- 도쿄 상권은 롱테일(신주쿠·시부야가 극단값)이라 z-score는 왜곡된다
- "상위 12%"는 사용자에게 즉시 이해되고 LLM 서술 재료로도 적합하다
- 감점 지표는 `100 − percentile`로 뒤집어 전부 "높을수록 좋음"으로 통일한다
- 결측은 중립값 50을 넣되 **결측 플래그를 남겨 화면에 "데이터 없음"으로 표기**한다.
  조용히 50점을 주면 거짓말이 된다

### 6.4 점수 계산

```python
# domain/service/scoring.py — 외부 의존 0, 순수 함수
def score(area: AreaMetrics, w: Weights) -> AreaScore:
    contributions = {
        k: w[k] * (area.percentile[k] - 50)
        for k in w
    }
    return AreaScore(
        total=50 + sum(contributions.values()),
        contributions=contributions,
    )
```

기여도를 저장하는 것이 핵심이다. 상위 3개·하위 3개를 LLM에 넘기면
"한식당이 상위 8%라 1위입니다"라는 설명이 나온다 — LLM이 이유를 지어내지 않는다.

**`Weights`의 키는 지표 15개다** (카테고리가 아니다). 다만 LLM에게 15개 값을
직접 채우게 하면 불안정하므로, `IntakeAgent`는 **사용자 관점 다이얼 5개**만 정하고
도메인의 고정 매핑 표가 이를 지표 가중치로 펼친다.

| 다이얼 | 펼쳐지는 지표 |
|---|---|
| 한국 생활 | 1, 2, 3 |
| 생활 편의 | 4, 5, 6 |
| 삶의 질 | 7, 8, 9, 10 |
| 가족 | 11, 12 |
| 비용·리스크 | 13, 14, 15 |

매핑 표는 `domain/service/scoring.py`에 상수로 두고 테스트한다. LLM은 다이얼
5개의 상대 강도만 정하므로 출력이 안정적이고, 최종 가중치 합은 1로 정규화된다.

### 6.5 가치 갭 회귀

```
log(시세중앙값) ~ 지표 1~12, 14, 15
잔차 = 실제 − 예측 → 음수가 크면 "인프라 대비 저평가"
```

**표본 250개에 변수 14개는 과적합하기 쉽다.** 따라서:

- 단순 선형회귀 대신 **Ridge**로 정규화
- 5-fold 교차검증 R²를 기록하고 **0.5 미만이면 이 기능을 비활성화**한다
- 출력에 항상 "통계적 추정이며 투자 조언이 아닙니다"를 강제 삽입

참고 기사가 R² 0.859를 얻은 것은 인구조사 구역 단위에 50개 변수를 쓴 조건이며,
본 프로젝트와 조건이 다르다. **돌려보고 기준에 못 미치면 접는다**를 설계에 명시한다.

## 7. 테스트 전략

도메인이 순수 함수이므로 LLM·네트워크 없이 전부 단위 테스트된다.

- 가중치가 0인 지표는 총점에 영향이 없다
- 모든 퍼센타일이 50이면 총점은 50이다
- 감점 지표가 높은 역은 점수가 낮아진다
- 가중치 합이 1이 아니면 정규화된다
- 결측 지표는 플래그가 남는다

에이전트 계층은 Fake 리포지토리로 통합 테스트한다.
