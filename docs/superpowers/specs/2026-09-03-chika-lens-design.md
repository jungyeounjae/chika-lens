# Chika Lens — 도쿄 생활 입지 분석 & 대화형 추천 에이전트

- 작성일: 2026-09-03
- 개정: 2026-09-04 — Places Insights(BigQuery)가 **개인에게 제공 불가**로 거절되어
  **Places Aggregate API**로 전환. §3, §6.2(지표 12), §8, §9, §10, §11 갱신.
- 상태: Phase 0 완료, Phase 1 진행 중

## 1. 배경과 목적

도쿄에 거주하는 한국인이 "어디에 살까"를 결정할 때, 일본어 부동산 사이트는
일본인 기준의 정보만 준다. 한국인에게 실제로 중요한 축(한국 식자재 접근성,
외국인 임대 난이도, 서울 어느 동네와 비슷한가)은 어디에도 정리되어 있지 않다.

본 프로젝트는 Google Places Aggregate API와 일본 공공데이터를 결합해
도쿄 역세권을 정량 평가하고, OpenAI Agents SDK 기반 대화형 에이전트로
한국인 관점의 지역 추천을 제공한다.

- 성격: 학습·포트폴리오 프로토타입
- 범위: 도쿄 23구
- 언어/스택: Python(에이전트·분석) + Next.js(채팅·지도)

## 2. 유스케이스

### 2.1 메인: 조건 대화 → 역세권 랭킹

사용자가 자연어로 조건을 말하면 에이전트가 가중치로 변환하고, 역세권 약 250개를
점수화해 상위 5곳을 지도와 함께 제시한다. 조건이 모호하면 **되묻고 확정한 뒤에만**
랭킹을 실행한다.

결과 화면이 답하는 것:

| 질문 | 근거 |
|---|---|
| 왜 여기가 1위인가 | 지표별 기여도 분해 |
| 실제 시세는 얼마인가 | MLIT 거래가격·지가공시 |
| 한국인이 많은가 | 구별 한국 국적 비율 (구 단위임을 명시) |
| 서울로 치면 어디인가 | LLM 서술 (데이터 아님, 감각 번역) |
| 단점은 무엇인가 | 감점 지표를 숨기지 않고 명시 |

### 2.1.1 특정 지역 조회

"히카리가오카 어때?"처럼 **조건 없이 한 지역을 묻는** 질문에 답한다.

실사용에서 드러난 누락이다. 원래 설계는 "조건 → 랭킹" 흐름만 상정했고,
`explain_area` 가 해시 `station_id` 를 요구하는데 에이전트가 이름을 id 로 바꿀
수단이 없었다. 그래서 랭킹 상위에 없는 역에 대해 **"데이터가 없다"고 답했다 —
실제로는 489개 역 전부에 지표가 있는데도.**

`lookup_station(name)` 이 이 구멍을 메운다. 부분 일치를 허용하고 정확히
일치하는 것을 먼저 둔다("新宿"은 新宿·新宿三丁目·西新宿을 모두 부른다).

**한글 음차는 LLM이 일본어로 바꿔서 넘긴다.** 역 마스터가 일본어 표기이므로
"히카리가오카"로는 찾지 못한다. 지침에 변환 예시를 넣었고, 0건이면 표기를 바꿔
한 번 더 시도한 뒤에 없다고 답하도록 했다.

### 2.2 파생

1. **후보지 비교** — 2~3곳을 나란히 놓고 차이 나는 축만 강조
2. **조건 되돌리기** — 예산·통근 조건만 바꿔 재랭킹 (대화 상태 유지)
3. **가치 갭 탐지** — 시세를 지표로 회귀시켜 저평가 역세권 발견

### 3.1 Places Aggregate API — 능력과 제약

Places Insights(BigQuery)를 쓰려 했으나 **개인 신청은 제공 불가**로 거절됐다(2026-09-04).
Google이 대안으로 제시한 Places Aggregate API로 전환한다.

`computeInsights` 한 번이 "이 영역 안에, 이 타입이고, 이 조건에 맞는 장소가 몇 개인가"에
답한다.

| 필터 | 값 |
|---|---|
| 영역 | 원(중심+반경) / 행정구역(place ID) / 임의 폴리곤 |
| 타입 | `includedTypes` / `excludedTypes` / `includedPrimaryTypes` (배열) |
| 영업상태 | `OPERATIONAL` / `PERMANENTLY_CLOSED` / `TEMPORARILY_CLOSED` |
| 가격대 | `FREE` ~ `VERY_EXPENSIVE` |
| 평점 | `minRating` / `maxRating` (1.0~5.0) |

응답은 `count`, 그리고 **count가 100 이하이면 `place ID` 목록**까지 준다.

**Insights 대비 잃는 것**

- **속성 필터가 없다.** `good_for_children` 같은 약 70개 속성을 쓸 수 없다.
  지표 12를 타입 기반으로 교체했다 (§6.2)
- **자유 SQL이 없다.** H3 그리드 집계, 타입별 일괄 집계 같은 것을 못 한다.
  필요한 조합마다 콜을 한 번씩 써야 한다

**Insights 대비 얻는 것**

- **4주 평가 기간이 없다.** 이전 설계의 최대 시한 리스크가 사라졌다
- **BigQuery 의존이 사라진다.** Analytics Hub 구독도, 데이터셋 권한도 불필요
- **place ID를 영구 보관할 수 있다** (캐싱 제한에서 명시적 면제). 한식당처럼
  희소한 카테고리는 count ≤ 100이라 실제 place ID가 오므로, "Insights에 이름이
  없다"는 문제가 구조적으로 해소된다
- **임의 폴리곤**을 쓸 수 있어, 나중에 원형 800m를 실제 도보권 폴리곤으로
  바꿀 여지가 생긴다

**남는 제약**

- **한국 식자재점 전용 타입은 여전히 없다** (`grocery_store`에 섞임).
  Places API Text Search로 1회성 배치 보완 — 이전 설계와 동일

### 3.1.1 비용과 갱신 주기

무료 5,000콜/월(Pro SKU), 분당 1,200콜.

**역이 489개다.** 초기 설계는 250개로 잡았으나 국토수치정보 실데이터로 역 마스터를
만들어 보니 도쿄 23구의 고유 역명은 489개였다(§6.1.1). 전부 매달 갱신하면
489 × 17 = **8,313콜**로 무료 한도를 66% 초과한다.

**해결: 갱신 주기를 지표별로 나눈다.**

| 배치 | 지표 | 콜 | 주기 |
|---|---|---|---|
| 코어 | 1, 4, 5, 6, 7, 8, 9, **11**, 12, 15 (10개) | **4,890** | 월 1회 |
| 다양성 | 10 (요리 8종) | 3,912 | 6개월 1회 |

근거는 데이터의 성질이다. 편의점·병원 개수는 달마다 움직이지만 **한 동네의 요리
구성비는 그렇지 않다.** 나카노가 일식 70%인 것은 반년 뒤에도 그렇다. 매달 다시
셀 이유가 없다.

부트스트랩 달에만 8,313콜로 한 번 초과하고(신규 계정 $300 크레딧으로 흡수),
그 뒤로는 코어 배치가 계속 무료 한도 안에 들어간다.

역 근접 통합으로는 해결되지 않는다 — 500m 이내를 전부 합쳐도 390역 × 17 =
6,630콜이고, 그러면 "신주쿠역"이 사라져 사용자가 말하는 단위와 어긋난다.

QPM 1,200 제한상 코어 배치는 최소 4분 소요.

**콜 수 감시:** 결제 보고서는 최대 24시간 지연되지만 Cloud Monitoring의
`serviceruntime.googleapis.com/api/request_count`는 수 분 내에 반영된다.
부트스트랩처럼 예산에 근접한 배치를 돌릴 때는 이쪽을 본다.

```bash
curl -s -G "https://monitoring.googleapis.com/v3/projects/<PROJECT>/timeSeries" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  --data-urlencode 'filter=metric.type="serviceruntime.googleapis.com/api/request_count" AND resource.labels.service="areainsights.googleapis.com"' \
  --data-urlencode "interval.startTime=<ISO8601>" \
  --data-urlencode "interval.endTime=<ISO8601>" \
  --data-urlencode 'aggregation.alignmentPeriod=86400s' \
  --data-urlencode 'aggregation.perSeriesAligner=ALIGN_SUM'
```

집계 수치의 보관 기한은 Aggregate API 정책 문서가 명시하지 않는다. Maps Platform
일반 약관의 **30일 캐시 제한**이 적용될 가능성이 높으므로, 인덱스를 **최소 30일마다
갱신**한다. 월 1회 배치이므로 실무상 제약이 아니다. place ID는 영구 보관 가능하다.

### 3.1.2 외부 데이터 취급 원칙

출처마다 재배포 권리가 다르므로 저장소 취급도 다르다.

| 데이터 | 출처 | 커밋 | 근거 |
|---|---|---|---|
| `stations.json` | 국토수치정보 | ✅ | 政府標準利用規約 — 출처 표기 조건으로 재배포 가능 |
| `ward_stats.json` | 도쿄도 통계 | ✅ | 東京都オープンデータ — 같은 규약 |
| `korean_shops.json` | Places API Text Search | ❌ | Google Maps 콘텐츠 |
| `metrics.json` | Places Aggregate API | ❌ | Google Maps 콘텐츠. 재배포 불가, 30일 캐시 제한 소지 |
| MLIT 시세·시설·재해 | 不動産情報ライブラリ | ❌ | 아래 서약 |

**MLIT에 대한 서약 (2026-09-07 회신):** API 이용 목적 확인 요청에 답하며
다음을 명시했다. 이후 설계는 여기에 구속된다.

- 취득 데이터는 **역권 단위로 집계해 0~100 점수로 정규화**해 쓴다
- **개별 거래·시설 데이터를 그대로 표시하거나 재배포하지 않는다**
- 자신의 환경 내에서만 보유하고 제3자에게 제공하지 않는다
- 출처로 "国土交通省 不動産情報ライブラリ"를 명시한다
- GitHub에는 **코드만 공개하고 취득 데이터는 포함하지 않는다**
- 초회 일괄 취득 후 월 1회 갱신, 상시 접근하지 않는다

따라서 MLIT 산출물도 `metrics.json`과 같이 `.gitignore` 대상이다.
"시세 데이터를 저장소에 넣자"는 판단이 나중에 나오면 이 서약이 제약이 된다.

**귀속 표기 의무:** 원시 카운트를 화면에 그대로 노출하면 "Google Maps" 표기가
필요하다. 다만 우리가 가공한 점수·퍼센타일에는 귀속이 불필요하다 —
정책상 "Google은 Google Maps 콘텐츠에만 귀속되며 당신의 값에는 아니다".

### 3.2 해상도 불일치 처리

랭킹 단위는 역세권이지만 국적별 인구 데이터는 구 단위까지만 존재한다.
같은 구 내 모든 역이 동일 값을 갖게 되므로:

- **주력 신호**: 한국 인프라 밀도 (역세권 해상도, Places Aggregate API)
- **배경 보정**: 구별 한국인 거주 밀도, 구별 외국인 비율 (낮은 가중치)
- 결과 화면에 "이 지표는 구 단위입니다"를 **명시 표기**한다

## 5. 에이전트 계층

### 5.1 핵심 원칙

**점수 계산은 도메인이 하고, LLM은 절대 계산하지 않는다.** LLM의 역할은
두 가지뿐이다 — (1) 조건을 `Weights`로 번역, (2) 결과를 한국어로 서술.
그래야 같은 조건에 같은 답이 나오고, 랭킹 로직을 LLM 없이 테스트할 수 있다.

### 5.2 구성: 2 에이전트 + in-process 핸드오프

A2A 프로토콜이 아니다. 같은 프로세스·같은 대화 이력 안에서 제어권만 넘긴다.

**`IntakeAgent`** — 조건 수집. 출력은 자연어가 아니라 구조화 타입.

```python
class SearchCriteria(BaseModel):
    commute_to: str | None
    commute_max_minutes: int | None
    budget_yen: tuple[int, int] | None
    household: Literal["single", "couple", "family"]
    weights: Weights
    hard_filters: list[str]
```

**`AnalysisAgent`** — 툴 호출과 결과 해석.

| 툴 | 유스케이스 | 데이터 |
|---|---|---|
| `rank_areas(criteria)` | RankAreas | BigQuery 사전 인덱스 |
| `explain_area(station_id)` | ExplainArea | 지표별 기여도 분해 |
| `compare_areas(ids[])` | CompareAreas | 차이 나는 축만 추출 |
| `detect_value_gap(filters)` | DetectValueGap | 회귀 예측가 vs 실거래가 |
| `lookup_places(station_id, category)` | LookupPlaces | Places API 실시간 |
| `lookup_station(name)` | — | 역 이름 → station_id (역 마스터) |

### 5.3 가드레일

1. **범위 이탈** — 도쿄 23구 밖 질문 거절 (데이터 없음 → 환각 위험)
2. **투자 조언 금지** — 데이터만 제시하고 판단은 사용자에게 반환.
   특히 가치 갭 출력에는 면책 문구를 강제 삽입
3. **수치 환각 차단** — 툴 결과에 없는 숫자가 서술에 등장하면 출력 검증에서 차단
4. **사실 환각 차단** — 숫자만이 아니라 **사실**도 툴 결과 안에서만 쓴다.
   시설의 이름·규모·명성, 분위기·평판·트렌드, 교통·소음·치안·건물 연식은
   모두 측정하지 않은 것이다. 값의 요약인 정성적 표현은 허용한다 (§6.4.1).
   "누구에게 맞는지"는 **가구 형태가 다이얼로 번역된 범위 안에서** 답한다
   (§6.4.2) — 금지되는 것은 측정하지 않은 특성을 근거로 든 적합성 판단이다
5. **기준 없는 종합 점수 금지** — 비교 기준이 제시되지 않은 조회에서는 툴이
   종합 점수를 넘기지 않는다 (§6.4.1)
6. **적용된 해석을 페이로드로 되읽어 준다** — 페르소나를 어느 가구 형태·다이얼로
   읽었는지 툴이 함께 넘긴다. 프롬프트로만 설명하게 하면 해석을 지어낸다 (§6.4.2)

### 5.4 프론트 연동

Agents SDK 스트리밍을 SSE로 전달하되 **텍스트와 툴 결과를 분리**한다.
`rank_areas` 반환 즉시 프론트가 지도에 핀을 찍고, 그 뒤에 서술이 타이핑된다.
지도가 설명보다 먼저 뜨는 편이 체감이 낫다.

**주변 역을 함께 찍는다.** 특정 지역 조회에서 반경 1.5km 안의 다른 역을 작은
회색 점으로 표시한다. 역 좌표가 이미 로컬에 있어 **API 비용이 0**이고, 점수로는
드러나지 않는 정보를 보여준다:

| 역 | 반경 1.5km 내 다른 역 |
|---|---|
| 光が丘 | **1개** (練馬春日町 1.3km) |
| 新宿 | **8개** (가장 가까운 것 353m) |

히카리가오카가 고립된 계획도시라는 것이 지도에서 바로 읽힌다.

**시설 위치 표시는 v2 후보다.** `searchNearby` 1콜에 카테고리 하나로
좌표·이름을 최대 20건 받을 수 있음을 실측으로 확인했다(슈퍼마켓 2건이
지표값과 일치). 다만 세 가지가 따라온다:

- **"런타임은 API를 부르지 않는다"는 전제가 깨진다.** 질문마다 Google을 호출한다
- **비용이 트래픽에 비례한다.** 질문당 3카테고리면 월 1,600질문까지 무료
- **귀속 표기가 의무가 된다.** 가공 점수는 면제지만 가게 이름을 그대로 띄우면
  "Google Maps" 표기가 필요하다

**지도는 두 경로 모두에 반응한다.** `rank_areas` 는 순위 번호가 붙은 핀 여러 개,
`explain_area` 는 번호 없는 핀 하나다. 처음에는 랭킹 경로만 배선해서, 특정 지역을
물으면 지도가 도쿄 전체만 보여주고 아무것도 하지 않았다 — 화면 절반이 놀았다.
`lookup_station` 을 뒤늦게 추가하면서 지도를 고려하지 않은 결과이고,
`explain_area` 페이로드에 좌표를 추가해 해결했다.

**구현 (2026-09-07):** `interface/api/` 에 FastAPI + SSE 엔드포인트를 만들었다.

| 이벤트 | 내용 |
|---|---|
| `tool` | 툴 반환값. 프론트가 지도·표를 그리는 재료 |
| `text` | LLM 서술의 증분 |
| `done` | 종료. 남은 일일 예산 포함 |
| `error` | 오류 코드와 메시지 |

러너를 주입 가능하게 뒀다. 실제 LLM 왕복은 키가 필요하고 돈이 들므로,
테스트는 가짜 러너로 스트리밍·가드·세션 경로를 전부 검증한다. 실제 OpenAI 호출은
`api/runner.py` 한 곳에서만 일어난다.

### 5.4.1 비용 보호 (스펙 §9 이행)

"IP당 rate limit과 일일 상한을 처음부터 넣는다"를 API 층과 함께 구현했다.

- IP당 분당 요청 수 제한 (기본 6, `CHIKA_RATE_PER_MIN`)
- 전체 일일 상한 (기본 200, `CHIKA_DAILY_CAP`)
- **가드는 스트림을 열기 전에 본다** — 거절된 요청은 에이전트를 돌리지 않으므로
  비용이 0이다
- 속도 제한을 일일 상한보다 먼저 검사한다. 거절된 요청이 일일 예산을 깎으면
  재시도만으로 하루치가 날아간다

둘을 함께 두는 이유: IP 제한만 있으면 분산 요청에 뚫리고, 일일 상한만 있으면
한 사람이 하루치를 다 쓸 수 있다.

프로세스 메모리 기반이라 인스턴스가 하나일 때만 정확하다. 확장 시 공유 저장소가
필요하다.

### 5.4.2 실사용에서 드러난 결함 (2026-09-07)

> 사용자: 히카리가오카는 살기 좋은 곳이야?
> 에이전트: (光が丘 분석)
> 사용자: **공원은 몇개가 있어?**
> 에이전트: **어느 역의 공원 수를 말씀하시나요?**

결함이 두 개였다.

**1. 대화 이력을 LLM에 넘기지 않았다.** `Runner.run_streamed(agent, message, ...)`
에 새 메시지 한 줄만 넘기고 있었다. `SessionState` 는 `SearchCriteria` 와
`last_ranking` 만 보관했고 **LLM 대화는 어디에도 저장하지 않았다.**
§5.5에 "Agents SDK 세션 메모리로 유지한다"고 적어놓고 실제로는 하지 않은 것이다.

→ `InMemorySession` 을 만들어 `Runner` 에 `session=` 으로 넘긴다.
SDK의 `OpenAIConversationsSession` 을 쓰면 대화가 OpenAI 서버에 보관되는데,
그건 개인정보를 남기기 시작하는 일이라 별도 결정이 필요하다. **프로세스
메모리에 두고 재시작으로 사라지게 한다.** 이력이 무한히 쌓이면 토큰 비용이 매
턴 늘어나므로 최근 40 아이템(대화 10턴 남짓)으로 자른다.

**2. 원시 개수를 툴이 돌려주지 않았다.** `explain_area` 가 백분위 99.2 만 주고
"68개"라는 숫자를 아예 모르고 있었다. 맥락이 있어도 "몇 개야?" 에 답할 수 없었다.

→ `MetricDetail.raw_value` 를 추가해 정규화 이전 값을 함께 싣는다.
지침에 "'몇 개야?' 라고 물으면 raw_value 를 쓴다 — 백분위는 순위이지 개수가
아니다"를 명시했다.

검증: 같은 대화가 이제 **"光が丘에는 공원이 68개 있습니다"** 로 답한다.

### 5.5 대화 상태

Agents SDK 세션 메모리로 `SearchCriteria`를 유지한다. "예산 12만엔으로 낮추면?"이
오면 해당 필드만 교체해 재랭킹한다 (유스케이스 2.2-2의 구현).

### 6.2.1 실측이 바꾼 두 지표 (2026-09-04, 나카노역 800m)

`scripts/probe_aggregate.py`로 실제 API를 때려 본 결과 지표 두 개가 설계대로는
쓸 수 없다는 것이 드러났다.

**지표 15 — `bar`·`night_club`을 뺐다.** 원래 구성(`storage`+`car_repair`+`bar`+
`night_club`)의 나카노 실측은 382였고, 분해해 보니 `bar` 310(65%) + `night_club`
105(22%)로 88%가 유흥이었다. 원래 의도한 창고·정비소는 39개(8%)뿐이다.

문제는 크기가 아니라 **신호의 방향**이다. `bar` 310은 "유흥가"가 아니라 "먹고 마실
데가 많은 동네"를 뜻하고, 도쿄 역세권에서 그건 대체로 장점이다. 감점으로 뒤집으면
활기찬 역일수록 벌점을 받는다. 게다가 `bar` 310은 `japanese_restaurant` 455와 같은
스케일이라, 요식업 밀도를 한 번은 플러스로 한 번은 마이너스로 이중 계상하게 된다.

→ `storage`+`car_repair`+`car_wash`+`truck_stop`으로 좁혔다(실측 39). 소음·대형차
통행·경관 측면에서 주거 쾌적성을 실제로 떨어뜨리는 것만 남겼다. 유흥의 소음은
가치판단이 갈리고 영업시간 데이터가 필요하므로 v2 과제로 미룬다.

**지표 10 — 종 수에서 유효 종 수로 바꿨다.** 원래는 count > 0인 타입 수였는데
나카노가 **8/8**이었다. 도쿄 23구에서 이 8개 타입이 하나라도 없는 역은 거의 없으므로
250개 역이 전부 만점이 되어 아무것도 구분하지 못한다.

→ 섀넌 엔트로피의 유효 종 수 `exp(-Σ p·ln p)`로 바꿨다. 한 타입이 압도하면 1에,
고르게 분포하면 타입 수에 가까워진다. **콜 수는 그대로**이고 계산만 다르다.
나카노는 일식이 70%(455/653)라 **3.13 / 8**이 나온다.

### 6.2.2 지표 변별력 실측 (2026-09-07, 표본 20역)

퍼센타일 정규화는 값이 서로 달라야 의미가 있다. 한 지표가 대부분의 역에서 같은
값이면 순위가 동률로 뭉개져 지표가 죽는다. 역 마스터에서 등간격 표본 20역을 뽑아
`scripts/probe_aggregate.py --distribution` 으로 확인했다.

| 지표 | 최소~최대 | 중앙 | 고유값 | 0인 역 | 판정 |
|---|---|---|---|---|---|
| `child_friendly_venue` | 0~13 | 4 | 10/20 | 2 | 충분 |
| `korean_restaurant` | 0~25 | 8 | 11/20 | 1 | 충분 |
| `supermarket` | 0~14 | 6 | 12/20 | 1 | 충분 |

**지표 12에 대한 우려는 기우였다.** 나카노의 3개가 예외적으로 낮았을 뿐,
중앙값은 4이고 최대 13까지 퍼진다.

`korean_restaurant`이 0~25로 가장 넓게 분포한다. 제품의 핵심 차별 지표가 실제로
지역을 가장 잘 구분한다는 뜻이므로, 설계 전제가 데이터로 뒷받침된다.

### 6.2.3 지표 2 실측: 검색어와 타입 필터 (2026-09-07)

`上野` 35개로 `新大久保` 34개를 앞섰고, 값이 34~35에 몰려 **포화**였다
(이론상 최대 40 = 2쿼리 × 20건 페이지 상한).

원인을 두 개 찾았다.

**1. `韓国コスメ` 검색어가 오염원이다.** 상업지구에서 일반 화장품점·드럭스토어·

텍스트 검색이 느슨하게 매칭해 "한국"과 무관한 소매 밀도를 재게 된다.

→ **`韓国コスメ` 를 뺐다.** 미용은 "어디 살까"의 판단 요소로도 약하다.
지표 이름을 "한국 식자재·미용 시설"에서 **"한국 식자재점"**으로 좁혔다.

**2. 타입 필터가 필요하다.** `韓国食品` 검색도 `deli`·`food_store`·`store` 같은

| 역 | 전체 | `asian_grocery_store` 만 |

| 上野 | 20 | 7 |
| 銀座一丁目 | 20 | **3** |

`grocery_store`·`supermarket` 까지 넓히면 한국 상품을 일부 취급할 뿐인 일반 슈퍼가

### 6.2.4 비용 안전장치와 필드 마스크 (2026-09-07)

**필드 마스크가 과금 티어를 정한다.** 지표 2가 `places.id,places.primaryType` 을
요청하고 있었는데, `primaryType` 하나 때문에 Text Search **Essentials(무료 무제한)**
에서 **Pro(월 5,000)** 로 올라가 있었다.

타입 필터를 응답이 아니라 **요청 파라미터 `includedType`** 으로 옮겨 해결했다.
비용만 준 것이 아니라 품질도 올라갔다:

| 역 | 응답 필터 | `includedType` |
|---|---|---|
| 新大久保 | 10 | **16** |
| 上野 | 7 | 6 |
| 銀座一丁目 | 3 | 4 |

응답 필터는 서버가 **20건으로 자른 뒤** 거르므로 매칭을 잃는다. 요청 필터는
자르기 전에 거른다.

489역 전체를 다시 수집한 결과 순위가 바뀌었다. 이전에는 日暮里(荒川区)가 1위였으나,
잘림이 사라지자 **新大久保·大久保(각 16)** 가 荒川 일대(9)를 앞섰다.
신주쿠구 코리아타운이 제자리를 찾은 것이고, 잘림이 상위권을 왜곡하고 있었다는 뜻이다.

**우리 예산 가드의 한계도 드러났고, 고쳤다 (2026-09-07).** `--max-calls` 는
"남은 작업량"만 보고 **"이미 쓴 양"은 몰랐다.** 재수집을 반복하는 동안 매번
"121콜이면 상한 5,000 안"이라고 통과시켰고 실제로는 한도를 넘겨 429를 맞았다.

이제 배치가 **Cloud Monitoring 에서 당월 사용량을 직접 조회**해 상한으로 쓴다.
조회에 실패하면 추측하지 않고 중단한다 — 틀린 값으로 예산을 계산하면 가드가
있는 척만 하게 된다. `--used-this-month` 로 직접 지정하거나 `--max-calls` 로
의도적으로 넘길 수 있다. **실수는 막고 판단은 남긴다.**

구현 주의: `gcloud` 는 PATH 의 `python3` 로 자기 코드를 돌리는데, uv 가 venv(3.12)를
PATH 앞에 두면 gcloud 448 이 3.12 에서 제거된 `imp` 를 import 하다 죽는다.
venv 를 PATH 에서 빼고 호출한다.

**GCP 레벨 쿼터 상한을 걸었다.** 그 전까지 일일 상한이 사실상 무제한이었다.
`--max-calls` 가드는 파이썬 코드 안에 있어서, 배치에 버그가 생기면 아무것도
막지 못한다.

| API | 일일 상한 | 근거 |
|---|---|---|
| `computeInsights` | 10,000 | 부트스트랩 8,313이 들어감 |
| Text Search | 2,000 | 지표 2가 489 |
| Nearby Search | 2,000 | 시설 표시(v2) 대비 |
| Autocomplete·GetPlace·Photo·Media·Reviews | 100 | 쓰지 않음. 사고 방지 |

되돌리려면 콘솔 → API 및 서비스 → 할당량에서 수정한다.

### 6.2.5 지표 11을 MLIT에서 Aggregate로 (2026-09-07)

"보육·교육 데이터 없음"이 실사용에서 계속 뜨길래 확인해 보니 **Google 에 이미
있었다.** MLIT 담당으로 배정한 것은 초기 설계의 추정이었고, 검증하지 않았다.

타입 후보 실측 (반경 800m):

| 타입 | 光が丘 | 西葛西 | 新宿 |
|---|---|---|---|
| `preschool` | 13 | **29** | 13 |
| `primary_school` | 5 | **7** | 1 |
| `child_care_agency` | 21 | 39 | 39 |
| `school` | 60 | 104 | **212** |

**`school` 은 쓸 수 없다.** 신주쿠 212는 학원·어학원이라 상업지구 점수가 된다.

표본 14역으로 두 조합을 비교해 `preschool` + `primary_school` 을 택했다.
`child_care_agency` 를 넣으면 상업지구가 부푼다 — 明治神宮前이 11에서 21로 뛴다.
변별력도 A가 낫다 (고유값 13/14 vs 12/14).

**콜 예산이 빠듯해졌다.** 코어가 10지표가 되어 489 × 10 = **4,890콜**,
무료 한도 5,000까지 여유가 **110콜뿐**이다. 프로브 한 번에 넘칠 수 있으므로
배치 전에 Cloud Monitoring 으로 당월 사용량을 확인한다.

**MLIT 가 오면 교체를 검토한다.** MLIT 는 인가 시설의 공식 등록부라 권위가 있고,
Google 은 인가외 시설과 학원을 섞어 볼 가능성이 있다. 다만 지금 비어 있는 것보다
측정된 값이 낫고, MLIT 가 끝내 오지 않아도 지표가 남는다.

**응답 파싱 주의:** `count`는 정수가 아니라 **문자열**로 온다(`"42"`). protobuf의
int64가 JSON에서 문자열로 직렬화되기 때문이다. 어댑터에서 `int()` 변환을 빠뜨리면
퍼센타일 정규화가 문자열 비교로 조용히 망가진다 — `"9" > "42"`가 참이 된다.

통근 시간은 지표가 아니라 **하드 필터**다. 상한을 넘는 역은 점수와 무관하게 제외된다.

### 6.2.6 지표 11을 다시 MLIT으로 (2026-09-08)

MLIT 키가 도착했다. 6.2.5에서 "MLIT 가 오면 교체를 검토한다"고 적어둔 대로
교체했고, 검토 결과는 **교체가 명백히 낫다** 였다.

**열려 있는 엔드포인트 (실측).** 문서 번호만으로는 무엇인지 알 수 없다 —
응답의 `_index` 필드에 데이터셋 이름이 들어 있어 그것으로 확인했다. 첫 조사에서
번호를 추측으로 붙였다가 절반이 틀렸으므로, 코드는 `_index` 접두사를 대조한다.

| 엔드포인트 | `_index` | 내용 |
|---|---|---|
| `XKT006` | `bs005_school` | 학교 |
| `XKT007` | `bs006_preschool` | 유치원·보육소 |
| `XKT010` | `bs007_medical_institution` | 의료기관 |
| `XKT011` | `bs008_welfare_facility` | 복지시설 |
| `XKT015` | `bs018_passengers_by_station` | 역별 승강객수 |
| `XKT025` | `bs028_liquefaction_tendency_map` | 액상화 경향 |
| `XKT027` | `bs033_storm_surge_area` | 해일 침수상정 |
| `XKT029` | `bs031_sediment_disaster_alert_area` | 토사재해 경계구역 |
| `XIT001` | (JSON) | 부동산 거래가격 — 2024년 도쿄도 57,960건이 1콜 |
| `XPT001` | (GeoJSON) | 같은 데이터의 좌표 포함 버전 |

`XPT001` 은 `from`/`to`(분기)가 **필수**이고 **z ≥ 15** 여야 한다. z=13은 400이다.

**타일 수집.** z=13에서 489역을 57타일로 덮는다. 같은 영역을 z=14로 넷으로
쪼개 받아도 고유 건수가 같았으므로 타일당 잘림은 없다. 역이 타일 경계에 붙어
있으면 반경 800m 안의 시설이 옆 타일에 있으므로 여유 1km를 두고 덮는다.

**구성.** 幼稚園·認定こども園·保育所·保育室 (`XKT007` 전량, 폐원 제외) +
`XKT006` 중 小学校·中学校·義務教育学校. 고교·대학·전수학교는 뺐다 — 아이를
키우는 가구가 통학 거리를 따지는 것은 초등·중학이고, 대학은 오히려 학생 거리의
신호라 다른 지표와 뜻이 겹친다. 도쿄 인접 지역까지 6,482곳.

보육시설에는 종별 **이름 필드가 없고 코드만 온다.** 표본을 훑어 하위 코드가
모두 보육 시설임을 확인했지만, 이름을 지어내지 않고 `保育施設(0504)` 처럼
코드를 그대로 붙인다.

**검증.** Google 값과 상관계수 **r = 0.857** — 두 출처가 강하게 일치하므로
MLIT 수집이 망가진 것이 아니다. 어긋나는 지점이 정확히 예상한 곳이었다.

| 역 | MLIT | Google | 성격 |
|---|---|---|---|
| 馬喰町 | 30 | 48 | 섬유 도매 상업지구 |
| 三越前 | 14 | 30 | 금융 오피스가 |
| 虎ノ門 | 1 | 9 | 오피스가 |
| 桜田門 | 0 | 4 | 관청가 |
| 菊川 | 42 | 42 | 주거지 — 일치 |
| 羽田空港第3 | 0 | 0 | 공항 — 일치 |

**주거지에서는 일치하고 상업지구에서만 Google 이 부푼다.** 6.2.5에서 `school`과
`child_care_agency` 를 뺀 판단이 옳았고, 남긴 두 타입에도 같은 왜곡이 덜한
형태로 남아 있었다는 뜻이다. MLIT 는 인가 등록부라 이 왜곡이 원천적으로 없다.

**부수 효과.**

- 코어 배치가 10지표에서 **9지표**로 줄어 월 4,890 → **4,401콜**. 무료 한도까지
  여유가 110콜에서 **599콜**로 늘었다. 크레딧이 2026-11-16에 만료되므로 그
  이후를 생각하면 이 여유 자체가 값어치가 있다.
- MLIT 는 호출 과금이 없다. 57타일 × 2데이터셋 = 114콜로 전량을 받는다.
- "학원이 섞여 있을 수 있다"는 주의문이 필요 없어졌다. 무엇을 세고 무엇을
  뺐는지가 코드에 남는다.

**산출물은 커밋하지 않는다.** `data/mlit_childcare.json` 과 원본 캐시는
gitignore 한다 — MLIT 에 회신한 이용 목적대로 역세권 집계값만 쓰고 개별 시설
레코드는 재배포하지 않는다 (§3.1.2).

**"뒤에 오는 파일이 앞을 덮는다"** 규칙으로 옛 `metrics.json` 의 Aggregate 값을
대체한다. 인덱스를 다시 접기 전에도 지표 11은 MLIT 값으로 나간다.

### 6.2.7 지표 13(시세) 구축 (2026-09-08)

`XPT001` 부동산 거래가격 정보. 호출 과금이 없고 z=13 에서 **57콜**이면 도쿄
23구 전역이 덮인다.

#### 엔드포인트 실측

| 항목 | 값 |
|---|---|
| 허용 줌 | z=11~15 (z=16 은 400) |
| 필수 파라미터 | `from`/`to` — 분기 문자열 `"20252"`. 없으면 400 |
| geometry | Point |
| `_index` | **없다.** 다른 XKT 엔드포인트와 달리 정체 필드가 없다 |
| 최신 데이터 | 2026 Q1 까지 (2026-09-08 기준). Q2 는 0건 |

z=13 한 타일과 그 자식 z=14 넷을 비교해 **레코드가 완전히 일치**하는 것을
확인했다 (좌표를 뺀 비교에서 양방향 차집합 0). 타일당 잘림은 없다.

`_index` 가 없으므로 클라이언트의 정체 대조가 통하지 않는다. 대신
`mlit_prices.parse_transaction` 이 필드 구성(`land_type_name_ja` 등 4개)으로
형태를 검증하고, 어긋나면 결측으로 접지 않고 던진다. `MlitDataset.index_prefix`
가 `None` 을 허용하되 **기본값을 두지 않는 것**은 새 데이터셋을 추가할 때
"정체를 확인했는가"를 반드시 마주치게 하기 위한 것이다.

#### 총액이 아니라 ㎡당 단가

응답의 총액은 매물 크기에 좌우된다 — 신주쿠 실측에서 45㎡ 8,400만엔과
15㎡ 1,100만엔이 같은 동네에 있었다. 총액 중앙값은 시세가 아니라 **그 동네에
흔한 매물 크기**를 재게 된다. 그래서 총액 / 전용면적으로 계산한다.

API 의 단가 필드(`u_transaction_price_unit_price_square_meter_ja`)는 쓸 수 없다
— 중고맨션 36,180건 중 채워진 것이 **51건**뿐이었다.

임대가 없다. 둘을 같은 것으로 취급하면 매매 단가가 월세로 표시되므로,
`build_real_session` 의 `PriceRepository` 는 계속 빈 Fake 다.

### 6.3 정규화: 퍼센타일 랭크

원시값을 그대로 쓰면 편의점 개수(0~80)가 재해위험(0~1)을 압도한다.
250개 역 안에서 퍼센타일(0~100)로 변환한다.

- 도쿄 상권은 롱테일(신주쿠·시부야가 극단값)이라 z-score는 왜곡된다
- "상위 12%"는 사용자에게 즉시 이해되고 LLM 서술 재료로도 적합하다
- 감점 지표는 `100 − percentile`로 뒤집어 전부 "높을수록 좋음"으로 통일한다
- 결측은 중립값 50을 넣되 **결측 플래그를 남겨 화면에 "데이터 없음"으로 표기**한다.
  조용히 50점을 주면 거짓말이 된다

### 6.4 점수 계산

```python
# domain/service/scoring.py — 외부 의존 0, 순수 함수
def score(area: AreaMetrics, w: Weights) -> AreaScore:
    contributions = {
        k: w[k] * (area.percentile[k] - 50)
        for k in w
    }
    return AreaScore(
        total=50 + sum(contributions.values()),
        contributions=contributions,
    )
```

기여도를 저장하는 것이 핵심이다. 상위 3개·하위 3개를 LLM에 넘기면
"한식당이 상위 8%라 1위입니다"라는 설명이 나온다 — LLM이 이유를 지어내지 않는다.

**`Weights`의 키는 지표 15개다** (카테고리가 아니다). 다만 LLM에게 15개 값을
직접 채우게 하면 불안정하므로, `IntakeAgent`는 **사용자 관점 다이얼 5개**만 정하고
도메인의 고정 매핑 표가 이를 지표 가중치로 펼친다.

| 다이얼 | 펼쳐지는 지표 |
|---|---|
| 한국 생활 | 1, 2, 3 |
| 생활 편의 | 4, 5, 6 |
| 삶의 질 | 7, 8, 9, 10 |
| 가족 | 11, 12 |
| 비용·리스크 | 13, 14, 15 |

매핑 표는 `domain/service/scoring.py`에 상수로 두고 테스트한다. LLM은 다이얼
5개의 상대 강도만 정하므로 출력이 안정적이고, 최종 가중치 합은 1로 정규화된다.

### 6.4.1 종합 점수의 한계와 노출 조건 (2026-09-08)

종합 점수는 15지표의 가중 평균이므로 **프로필이 양극단인 동네를 평균으로
뭉갠다.** 光が丘(練馬区) 실측:

| 지표 | 원시값 | 백분위 |
|---|---|---|
| 공원 | 68 | **99.2** |
| 혐오시설 | 19 | 86.8 |
| 보육·교육 | 24 | 71.5 |
| 의료 | 46 | 30.4 |
| 슈퍼 | 2 | 16.3 |
| 편의점 | 11 | **10.6** |
| 카페 | 2 | **9.3** |
| 피트니스 | 2 | **8.3** |

- 균등 다이얼: **39.9점**
- 육아 다이얼 최대(FAMILY 5, DAILY_CONVENIENCE 3): **40.1점**

**다이얼을 극단으로 돌려도 0.2점 움직인다.** `childcare_education` 71.5 가
`child_friendly_venue` 33.8 과 일상편의(10.6, 16.3)에 상쇄되어 어떤 가중치로도
40점 근처에 갇힌다. 즉 "육아하기 좋아?"에 시스템은 "평균 이하"라고 답한다.
게다가 지금은 15지표 중 3개(시세·재해위험·요리다양성)가 결측이라 **점수의
20%가 50.0 자리채움**이다.

문제는 백분위가 아니다. 공원 68곳 / 백분위 99.2 는 개수만으로는 알 수 없는
것을 알려주는 유용한 정보다. **하나의 절대 점수로 접는 순간 정보가 파괴된다.**

#### 결정

`explain_area` 는 **그 역이 방금 만든 랭킹에 있을 때만** `score` 를 넘기고,
아니면 `score_omitted: "no_reference_set"` 을 넘긴다.

| 상황 | 종합 점수 | 근거 |
|---|---|---|
| 랭킹 결과의 "왜 여기가 1위야" | 준다 | 그 점수가 순서를 만들었고 비교 대상이 함께 있다 |
| 이름으로 한 동네만 조회 | 안 준다 | 기준 없는 절대 점수는 오해만 만든다 |
| `compare_areas` | 준다 | 비교가 질문 자체다 |

백분위와 `raw_value` 는 그대로 남긴다 — **숨기는 것이 아니라 뭉개지 않는
것이다.** 감추면 오해를 만드는 모델은 그대로 두고 증거만 없애는 셈이 된다.

프롬프트로 "점수를 말하지 마"라고 적는 대신 **페이로드에서 뺀다.** 보이면
쓴다 (§5.3의 "가드레일은 프롬프트가 아니라 코드에" 원칙).

조건이 바뀌면 `set_criteria` 가 `last_ranking` 을 비우므로 옛 순위를 근거로
점수가 계속 나가는 일도 없다.

#### 정성적 서술의 경계

점수를 빼면 답변은 정성적으로 서술해야 한다. 그런데 LLM 이 사전학습 지식으로
문장을 쓰면 **숫자 환각보다 나쁘다** — 틀려도 그럴듯하게 읽혀 검증할 방법이
없고, 그 답변은 범용 챗봇에 물어도 나오므로 데이터 파이프라인 전체가 장식이
된다. 그래서 새 사실 도입은 금지하고 **값의 요약**만 허용한다.

- 허용: "공원 68곳으로 최상위권. 반면 편의점 11곳·슈퍼 2곳·카페 2곳으로
  상업 시설이 얇은 곳입니다." → "얇다"는 낮은 백분위 3개의 요약이다
- 금지: "대형 공원을 품은 계획 주거 단지로, 유흥가가 없어 조용합니다."
  → 규모·단지 성격·유흥 모두 데이터에 없다. 특히 `nuisance_venue` 는
  창고·정비소·세차장이며 **유흥·야간 업소가 아니다**

쓸 수 있는 말이 없으면 "그건 이 데이터로 알 수 없습니다"로 답한다.

#### 남은 문제 — 표현으로 못 고치는 것

光が丘의 편의점 백분위 10.6 은 **계획 단지가 상업 시설을 한 곳에 모은
결과**다(光が丘IMA 등). 반경 800m 개수 세기는 흩어진 동네를 높게, 집중된
동네를 낮게 평가한다. **개수 지표가 상업 밀도를 재고 그것을 생활 편의의
대리 지표로 쓰는 것**이 뿌리다. 산문으로 덮을 수 없다 (§11-10).

### 6.4.2 페르소나 질문 — 가구 형태를 다이얼로 번역한다 (2026-09-08)

"大久保는 신혼부부가 살기 좋은 동네야?" 에 시스템은 **"이 데이터만으로 단정할
수 없습니다"** 로 답했다. 원인이 셋이었고 서로 독립적이었다.

1. **IntakeAgent 의 독해 표에 가구 형태를 가리키는 말이 없었다.** "아이"·"육아"
   는 있어도 "신혼부부"·"부부"·"1인" 은 어느 행에도 맞지 않았다. 다이얼이 앞
   턴(`korean_life` 5) 그대로 남아 **조건이 전혀 바뀌지 않았고**, 그래서 답변의
   근거가 여전히 한식당·한국 식자재점이었다. 서술 톤이 아니라 계산이 문제였다.
2. **`household` 는 받아도 효과가 0 이었다.** 코드 전체에서
   `median_rents(criteria.household)` 한 곳에만 쓰였고, 실데이터에서 월세
   리포지토리가 빈 Fake 다. `couple` 로 설정해도 점수는 1원어치도 안 움직였다.
   조건을 받는 척만 하는 필드였다.
3. **규칙 1-1 이 페르소나 질문 자체를 차단했다.** "누구에게 맞는지 — '신혼부부에게
   알맞다' 같은 판단의 근거 데이터가 없습니다" 라고 명시적으로 금지되어 있었다.
   §6.4.1 의 환각 방지가 과잉 교정된 것으로, 규칙 10 이 랭킹 경로에서 고친 것과
   같은 결함이 `explain` 경로에 남아 있었다.

#### 결정 — 말은 LLM 이 읽고, 정책은 코드가 정한다

페르소나 표현은 무한하다(신혼부부·자취생·유학생·노부부…). 그것을 **세 값 중
하나로 옮기는 일**은 자연어 이해이므로 LLM 이 한다. 그 값이 **어느 축을 뜻하는지**
는 `domain/service/personas.py` 의 `HOUSEHOLD_DIALS` 가 정한다. 프롬프트에 다이얼
숫자를 적으면 매번 다른 값이 나오고 테스트할 수도 없다.

| 가구 형태 | 생활 편의 | 생활 환경 | 육아 환경 | 비용·위험 |
|---|---|---|---|---|
| `single` | 3 | 3 | **0** | 3 |
| `couple` | 3 | 3 | **2** | 3 |
| `family` | 4 | 3 | **5** | 3 |

- `couple` 의 육아 환경을 0 이 아니라 **2** 로 둔다. 보육·교육은 아이가 있어야만
  쓸모 있는 것이 아니라 몇 년 뒤를 보는 축이고, 신혼부부가 실제로 보는 것이다.
  5 로 두면 아이 있는 가구와 구분이 사라진다.
- `korean_life` 는 어느 가구 형태에도 넣지 않는다. 가구 형태와 무관하고,
  사용자가 말했을 때만 켜져야 한다.

**채우는 것은 사용자가 침묵한 축뿐이다** (`seed_dials`). "아이 학교가 중요해요"
로 켠 육아 5 를 뒤이은 "저희는 부부예요" 가 2 로 **내려서는 안 된다** — 직접 말한
것이 통계적 기본값보다 강하다. 반대로 침묵한 축의 0 은 "안 본다" 는 뜻이고,
가구 형태를 말한 사용자가 뜻한 것은 그게 아니다. 씨딩은 **`household` 를 넘긴
턴에만** 일어난다. 매 턴 채우면 사용자가 다이얼을 0 으로 되돌릴 방법이 없어진다.

#### 해석을 페이로드로 되읽어 준다

`set_criteria` 는 `interpretation` 을, `explain_area` 는 `criteria` 를 함께
넘긴다 — `household` 라벨, 강도 0 이 아닌 다이얼, 그 조건에서 보는 지표 이름.
프롬프트에 "해석을 설명하라"고만 적으면 LLM 이 **해석을 지어낸다**. 실제 적용된
값을 내려야 서술과 계산이 어긋나지 않고, 사용자가 "아니 우리는 아이 계획이
있어요" 라고 고칠 수 있다.

에이전트 규칙 11 은 답변 순서를 고정한다: (1) 무엇으로 읽었는지 한 줄,
(2) 그 조건의 지표로 장점과 단점을 **둘 다**, (3) 마지막에 한계(결측 지표와
측정하지 않는 것). **"단정할 수 없습니다" 로 시작하지 않는다** — 조건이 지표로
번역되어 있고 값도 있는데 판단을 거부하면 사용자는 답도 데이터도 못 받는다.
한계는 결론과 **함께** 말하는 것이다 (§6.4.1 의 규칙 10 과 같은 원칙).

규칙 1-1 의 금지는 "누구에게 맞는지" 전체가 아니라 **측정하지 않은 특성을
근거로 든 적합성 판단**으로 좁혔다 — "신혼부부가 좋아할 분위기" 는 여전히
금지고, "부부·2인 가구 조건에서 보육·교육 백분위 45.0" 은 허용이다.

#### 함께 잡은 결함 — 분수 지표의 단위

`korean_resident_ratio` 는 `한국 국적자 / 구 인구` 라 0.025811 로 저장되는데
`METRIC_UNITS` 는 "%" 였다. 실사용에서 **"한국 국적 비율 0.025811%"** 가 나갔다 —
실제 2.58% 를 100배 작게 말한 것이다. 백분위는 단조 변환에 영향받지 않아 랭킹은
옳았고 **서술만 틀렸다**. 그래서 인덱스를 다시 굽지 않고 표시 단계에서 옮긴다
(`metrics.display_raw_value`, `RATIO_METRICS`). 지표 13(시세)을 붙이며 단위를
도입할 때 놓친 것으로, 단위 표에 "%" 를 적었다는 사실이 값이 %라는 뜻은
아니었다.

### 6.5 가치 갭 회귀

```
log(시세중앙값) ~ 지표 1~12, 14, 15
잔차 = 실제 − 예측 → 음수가 크면 "인프라 대비 저평가"
```

**표본 250개에 변수 14개는 과적합하기 쉽다.** 따라서:

- 단순 선형회귀 대신 **Ridge**로 정규화
- 5-fold 교차검증 R²를 기록하고 **0.5 미만이면 이 기능을 비활성화**한다
- 출력에 항상 "통계적 추정이며 투자 조언이 아닙니다"를 강제 삽입

참고 기사가 R² 0.859를 얻은 것은 인구조사 구역 단위에 50개 변수를 쓴 조건이며,
본 프로젝트와 조건이 다르다. **돌려보고 기준에 못 미치면 접는다**를 설계에 명시한다.

## 7. 테스트 전략

도메인이 순수 함수이므로 LLM·네트워크 없이 전부 단위 테스트된다.

- 가중치가 0인 지표는 총점에 영향이 없다
- 모든 퍼센타일이 50이면 총점은 50이다
- 감점 지표가 높은 역은 점수가 낮아진다
- 가중치 합이 1이 아니면 정규화된다
- 결측 지표는 플래그가 남는다

에이전트 계층은 Fake 리포지토리로 통합 테스트한다.

### 8.1 Aggregate 배치 실측 (2026-09-07)

역 3개(신오쿠보·나카노·세타가야) × 코어 9지표 = 27콜로 엔드투엔드를 확인했다.

| 지표 | 新大久保 | 中野 | 世田谷 |
|---|---|---|---|
| `korean_restaurant` | **234** | 9 | 1 |
| `cafe` | 163 | 50 | 31 |
| `supermarket` | 24 | 4 | 1 |
| `child_friendly_venue` | 11 | 3 | 0 |

**한식당 234 vs 9 vs 1.** 핵심 차별 지표가 도쿄 코리아타운을 정확히 짚어낸다.

파이프라인 전체(배치 → 인덱스 → 리포지토리 → 정규화 → 스코어링 → 설명)가
실데이터로 돌았고, 다이얼을 "한국 생활"에서 "가족"으로 바꾸면 1위 근거가
한식당에서 아이 동반 시설로 갈아끼워지는 것도 확인했다.

**Phase 2가 승인 대기에서 풀렸다.** Aggregate API는 결제 계정과 API 키만 있으면
즉시 쓸 수 있으므로, MLIT 승인을 기다리지 않고 Phase 1과 병행할 수 있다.

Phase 0 종료 시점에 **가짜 데이터로 에이전트가 대화하고 랭킹을 내놓는 것까지**
확인된다. 데이터가 들어오면 리포지토리 구현체만 교체한다.

### 8.3 드러난 문제: 주거 대상이 아닌 역

비용·리스크 다이얼이 공항·크루즈터미널·관청가를 상위로 올린다. 원인이 둘이다.

**원인 1 — 지표 2/3가 결측.** `price_level`·`disaster_risk`가 MLIT 대기라 중립값
50이고, 실질적으로 `nuisance_venue` 하나로 순위가 정해진다. 공항에 창고가 없는
것은 당연하다. **MLIT가 들어오면 시세가 이 다이얼을 지배하므로 해소된다.**

**원인 2 — 역 489개에 주거 후보가 아닌 역이 섞여 있다.** 이건 MLIT로 안 풀린다.

생활 인프라 밀도로는 구분되지 않는다 — 공항에는 편의점과 클리닉이 많다.
**판별 신호는 `supermarket`이다:**

| 역 | 편의점 | 슈퍼 | 의료 |
|---|---|---|---|
| 羽田空港第3ターミナル | 8 | **0** | 2 |
| 東京国際クルーズターミナル | 14 | **0** | 2 |
| 桜田門 | 20 | **0** | 10 |
| 新大久保 | 84 | 24 | 112 |
| 西葛西 | 28 | 10 | 86 |

편의점은 통행량만 있어도 생기지만, 슈퍼는 **일상 장을 보는 사람**이 있어야 생긴다.

**미결 — 어떻게 처리할지 판단이 필요하다:**

- (a) `supermarket == 0` 을 하드 필터로 — 단순하지만 임계값이 임의적이다
- (b) MLIT 거래 데이터가 0건인 역을 제외 — "집이 없는 곳에는 살 수 없다"는
  원칙적 근거가 있지만, **"결측은 탈락시키지 않는다"는 기존 규칙과 충돌한다.**
  "데이터를 못 받았다"와 "주택시장이 아예 없다"는 다른 정보인데, 지금 설계는
  둘을 구분하지 않는다
- (c) 수동 제외 목록 — 확실하지만 유지보수가 필요하다

(b)가 원칙적으로 옳아 보이나, 결측 처리 규칙을 손대는 일이므로 MLIT 데이터를
실제로 본 뒤에 결정한다.
